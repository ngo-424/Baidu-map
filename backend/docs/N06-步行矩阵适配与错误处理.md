# N06：步行矩阵适配、顺序还原与错误处理

状态：**技术完成，已加入 50 点以上回归；真实百度调用待后续权限核验**

## 实现方式

百度 DirectionLite 步行接口一次接收一个起点和一个终点，不提供本项目所需的多终点矩阵响应。因此 N06 的“矩阵”在适配层表示为同一起点的一组逻辑目的地，由 `Scheduler.observe_many()` 拆成受并发限制的小批次，逐个调用 `BaiduProvider`，再按输入顺序返回结果。

实现入口：

- `life-circle-algorithm/src/life_circle/scheduler.py`：批次切分、并发、顺序还原、缓存、预算和重试；
- `life-circle-algorithm/src/life_circle/providers.py`：单起点/单终点百度步行请求和响应解析；
- `life-circle-algorithm/src/life_circle/models.py`：`RouteObservation` 和统计字段。

## 处理规则

- 批次大小由 `IsochroneRequest.concurrency` 控制，默认 2；下一批只有在当前批完成后才会安排，避免完成先后改变预算分配。
- 输入点先归一化到六位小数并去重；缓存命中不占新调用预算，返回列表仍与原输入一一对应。
- 每一次实际 Provider 调用都先占用预算；重试同样占用预算并计入 `retries`、`requests` 和 `network_requests`。
- 超时、临时错误和限流最多重试一次；权限、参数、无结果和无效响应不重试，保留明确 `reason`。
- 单点失败不伪造耗时或不可达，返回 `duration=null` 的 `RouteObservation`，算法后续将其作为 unknown；连续临时失败达到阈值或配额/权限失败时停止新增采样。
- 百度响应中的路线时长取有效路线最短值；分段首尾端点偏移超过 50 米时丢弃该路线并标记 `endpoint_offset`。

## 验收样例

`life-circle-algorithm/tests/test_contracts.py::test_n06_50_destination_batch_preserves_order_and_explicit_unknowns` 使用 50 个目的地验证：

- 返回目的地顺序与输入完全一致；
- 预算上限为 60，实际调用包含 3 次临时错误重试且不超过上限；
- 一个明确无结果的点保留 `no_result`，其余点正常返回；
- Provider 实际调用数与统计 `requests` 一致。

百度适配器的请求参数、HTTP 状态、业务状态、路线结构、端点偏移和重试边界由 `tests/test_baidu.py` 覆盖。上述测试全部使用 `httpx.MockTransport`，不会访问真实百度或消耗配额。

## 限制与后续

N06 证明的是本地逻辑矩阵适配和故障处理，不证明真实百度步行权限、QPS 或路线精度。真实实验必须先配置已确认的服务端 AK 和 QPS，并按 N01 已确认的 `≤900 秒`、步行路线距离 `≤1000 米`、100 米容差及 `isochrone` 评估范围执行。
