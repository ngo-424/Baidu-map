## 6. 严格 QPS 问题、修复与限制

### 本次真实运行未通过严格 QPS

完整分析发送账本的最短相邻间隔约 **0.328 秒**，个别滚动 1 秒窗口内最多 **4 次发送**，未满足严格 3 QPS。初步完成提示中的“未触发连续故障停止”不能作为 QPS 合规证据；该问题是在完整账本复核时发现的。

本机 Python 3.11 的 monotonic 时钟分辨率为 **0.015625 秒**。旧代码等待一次后直接放行，没有再次比较实际时钟与目标发送时间。[Python 事件循环文档](https://docs.python.org/3/library/asyncio-eventloop.html#asyncio.loop.call_later) 说明延迟回调可能提前一个时钟分辨率触发；提前唤醒模拟测试在三处旧逻辑上均失败，复现了该缺陷。

本次 5 次百度限流响应与发送间隔问题同时出现，但没有百度侧完整配额和计费窗口记录，不能认定这就是全部限流响应的唯一原因。

### 已完成的修复

- `backend/app/analyses.py`：共享 RateGate 在锁内重新检查发送时刻，并再次检查截止时间。
- `life-circle-algorithm/src/life_circle/scheduler.py`：等待提前返回时继续等待，同时保留取消和截止检查。
- `backend/tools/live_smoke.py`：HTTP 发送前再次检查时刻，取消或预算保护仍有效。
- 对应测试先失败再通过，没有改变 QPS 配置值、业务接口、采样评分和预算。

修复后的本机真实时钟验证使用 MockTransport 与本地 Provider，各 20 次，**零百度调用**：

| 验证对象 | 最短相邻间隔 | 滚动 1 秒最大发送数 |
| --- | ---: | ---: |
| 共享 RateGate | 0.338623 秒 | 3 |
| 算法 Scheduler | 0.335099 秒 | 3 |
| 发送保护 Transport | 0.339606 秒 | 3 |

因此本项状态为：**真实运行发现失败 → 代码已修复 → 离线复核通过 → 修复后的百度线上复核未执行**。本轮不追加第二次 200 次任务，也不拿其他阶段剩余配额做额外分析。
